# ADR-0022：`init`/`budget` 主动放宽熔断阈值的语义裁决

- **ID**：ADR-0022
- **对应审计项**：#22（R3， harness-iteration-loop.md §10.2 台账）
- **状态**：ACCEPTED（护栏已实现并通过自动验证；语义裁决属人工确认点，见 §6）
- **决策日期**：2026-11-18
- **相关契约**：registry `Loop 终止硬上限`（turns/tokens=告警层；max_time/failures=终态熔断层）

## 1. 背景（Context）

审计 #22 实锤：`fail --max-failures` 的逐次抬高后门已在 v2.5.4（R6 P0-2）封堵——
`fail` 只允许**收紧**熔断阈值，放宽一律忽略并告警（锁定于 `test_state_runtime_sequencing.py` T4/T5 + N2）。

但 registry 明确授权 `init`（开局一次性设定）与 `budget`（运行期调整）为**上限写入口**。
因此 `budget --max-failures 99` 或 `init --max-failures 99` 仍能主动放宽熔断阈值，
使熔断在 99 次失败后才触发——审计台账 §10.2 #22 标「未闭环·设计语义·登记备查」。

## 2. 问题（Problem）

要杜绝「主动放宽」有两种路径，但代价不同：

- 若直接禁止 `init`/`budget` 放宽（rc=1 拒绝），属 **registry 语义变更 + 行为破坏**：
  `budget` 本就是「跑起来后上调预算」的合法入口，运行期发现任务比预期复杂而上调
  `max_failures`/`max_time` 有其真实场景；一刀切拒绝会破坏向后兼容。
- 若维持现状零处理，则「放宽熔断」完全静默，调用方无法察觉熔断阈值已被抬高——
  与 R6 封堵 `fail` 后门时的「不允许静默」原则不一致。

## 3. 裁决（Decision）

**维持「放宽允许」的 rc 语义（不改行为、不拒绝写入），但新增告警 + 留痕护栏**，
与 `fail` 的「放宽忽略并告警」形成语义闭环：

1. **熔断层**（`max_failures`、`max_time`）：`init`/`budget` 放宽时——
   - stderr 打印 `⚠️ 熔断阈值被放宽（#22）: ...` 告警；
   - 写入状态 `notes` 留痕（带时间戳 + 阶段），可追溯、可观测；
   - **rc 保持 0，写入照常生效**（registry 授权入口，向后兼容）。
2. **收紧**：静默放行，不告警不留痕（收紧是合规操作，非风险事件）。
3. **告警层**（`turns`、`tokens`）：放宽不触发本护栏（R7 P1-1 分层：二者是主理人
   语义裁量的告警层，不改变终态熔断语义）。
4. **`fail` 后门**：保持 v2.5.4 语义不变（只允许收紧，放宽忽略并告警），不因本 ADR 回退。

 rationale：R6 封堵的是「绕过 registry 授权的逐次抬高后门」，本 ADR 处理的是
「registry 已授权的写入口」——两者性质不同，但都须让「放宽熔断」可观测。
护栏把决策权交还主理人（告警提示）而非代码硬拒绝，契合「管家节点做语义判断」的分工宪法。

## 4. 实现（Implementation）

- `state_io.py` 新增 `_warn_relaxed_ceilings(before, after, cmd)` 纯函数：比对覆写前后
  `budget` 的熔断层阈值，放宽则返回告警文案并打印 stderr；收紧/告警层不触发。
- `cmd_init`：以默认阈值为基线，设定值放宽则告警 + `notes` 留痕。
- `cmd_budget`：覆写前拍快照，覆写后比对，放宽则告警 + `notes` 留痕。
- 锁定测试 `tests/test_ceiling_relaxation_guard.py`（6 组注入用例 R1–R6，全绿）。

## 5. 后果（Consequences）

- **正面**：熔断放宽不再静默；`fail` 后门与授权入口语义对齐；rc 语义零破坏。
- **负面**：`notes` 新增放宽留痕条目（ append-only，不影响既有字段读者）；
  熔断放宽仍「合法」——本 ADR 未杜绝放宽，只让其可见（杜绝放宽属行为变更，另开轮次）。
- **风险接受**：若主理人忽略告警把阈值放宽到极大值，熔断仍会失效——但此时是
  **有记录的语义裁量**（notes + stderr），不再是静默盲区，符合管家节点责任制。

## 6. 状态说明（四态纪律）

- **自动验证通过**：6 组注入测试 + 既有 4 套 state 门禁（ceilings/runtime/file/protocol）全绿。
- **语义裁决（待人工确认）**：「放宽允许」这一语义本身是人工裁决点——本 ADR 记录的是
  AI 依据 registry 语义与向后兼容原则给出的 ACCEPTED 结论，**管家节点可推翻**
  （若改判「禁止放宽」，则另开行为变更轮次，rc 语义与测试同步调整）。
